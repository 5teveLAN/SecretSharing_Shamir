附錄 2-1 · 技術選擇

為什麼是原生 HTML / CSS / JS

  • HTML
  • CSS
  • JavaScript

整個系統就是一個網頁：Canvas 讀像素、 純函式算數學、DOM 做介面。 瀏覽器直接就是執行環境，不需要建置、不需要後端，也沒有任何資料離開你的電腦。

零依賴
沒有打包工具、沒有 npm 套件，所有運算都跑在瀏覽器裡。 GF(28) 查表只用兩個 256 格的 Uint8Array。

01 · 動機

組員都不熟 JS

比起框架，先看懂一支不到 100 行、只做數學的模組更容易；錯了也能一行一行 debug。

02 · 跨平台

有瀏覽器就能跑

桌機、手機、投影機都能開；要分享給別人，丟一個網址就好。

03 · 沒有後端

機密不離開本機

圖片只在記憶體與 Canvas 裡處理、不上傳伺服器 —— 符合機密分享「自己保管 share」的精神。

04 · 分工

檔案邊界＝人的邊界

附錄 2-2 · 分層

每層只知道它下面那層

1 · 影像層

ui.js

知道哪張圖是第幾號 share、怎麼畫到 Canvas。逐像素、逐通道呼叫下一層， 不寫任何數學。

2 · 演算法層

shamir.js

吃 0–255、吐 0–255：抽係數、Horner 求值、呼叫拉格朗日取 a0。 不知道什麼叫圖片。

3 · 數學層

gf28.js

只有四則運算與兩張查表陣列。換成假的實作，上層照樣能跑。

4 · 瀏覽器層

Canvas API

讀像素、畫像素、匯出 PNG；全部在瀏覽器裡完成，沒有後端。

為什麼迴圈放在 ui.js？
因為「哪張圖是第幾號 share」是介面的概念。這樣 shamir.js 只認得數字，可以完全不碰 Canvas，也才能在 Node 裡用單元測試直接驗證。

附錄 2-3 · 介面規格

先把幾個函式講好，其他都自由發揮

gf28.js add / sub / mul / div(a, b) → number
shamir.js generateShares(value, k, n) → number[]
shamir.js reconstructPixel(points, k) → number
ui.js generateSharesAll(imageData, k, n) → ImageData[]
ui.js reconstructAll(imageDataList, k) → ImageData

規格只寫 函式名 / 輸入 / 輸出；底層用物件、class 還是純函式，不影響別人。 回答不出參數與回傳值的，就不是規格，是願望。

  • 1 值域寫死 像素值一律 0–255 的整數；1 ≤ k ≤ n ≤ 255； share 的座標 x 從 1 開始（0 是秘密本身）。
  • 2 邊界有定義 div(a, 0)、k > n、share 張數不足都直接拋錯， 而不是默默回一張錯的圖。
  • 3 不改別人的資料 generateShares 不動輸入； generateSharesAll 一律回傳新的 ImageData，原圖保持原樣。
  • 4 可以互換假貨 安 還沒寫好前，蕭 用假的 GF28 先跑； 蕭 還沒寫好前，妡 用假的 generateShares 先做畫面。

附錄 2-4 · 分工

一個檔案，一個人，互不阻塞

每人只維護一支檔案，靠那幾個函式當接縫；誰先完成都不會卡住其他人。

安 · 數學層

code/gf28.js

模組載入時建 exp / log 兩張表， 提供 add / sub / mul / div。加法是 XOR、乘除查表， 本原多項式 0x11d（x8+x4+x3+x2+1）。

蕭 · 演算法層

code/shamir.js

用 crypto.getRandomValues 抽亂數係數， Horner 法求 f(1)…f(n)； 還原交給 code/Lagrange.js 取 f(0) = a0。

妡 · 影像與介面層

code/ui.js

逐像素、逐通道呼叫上面兩層；負責 Canvas 顯示、上傳與拖曳、 分享圖下載、還原預覽，以及所有錯誤提示。

接縫處的約定：shamir.js 從 ./gf28.js 匯入 GF28； ui.js 從 ./shamir.js 匯入兩個函式。 匯出名稱對齊，換人接手也不必改程式。

附錄 2-5 · 開發流程

我們怎麼用 AI 和 GitHub 協作

  • 1 AI 先出「骨架」 因為都不熟 JS，請 AI 先寫三支檔案的介面草稿（只有函式簽名與註解）， 先確定接得起來，再各自填內容。
  • 2 用 AI 補細節、自己驗證 查表、Horner、Canvas 這類細節請 AI 給初版； 數值對不對一定自己再算一次（例如 0x57 × 0x83 = 0x31）。
  • 3 規格變成可執行的測試 同一份介面規格寫成 BDD（給人看的 Gherkin）與單元測試； 跑一次 npm test 就知道有沒有壞。
  • 4 分支 + Pull Request 一人一條分支、一個功能一個 commit；合併前先跑測試，衝突就在合併時解決。

terminal

# 一人一條分支
git switch -c feat/gf28
# 改完先跑測試
npm test        # 21 pass
npm run bdd     # 23 scenarios
# 小步驟 commit，訊息寫清楚改了什麼
git add code/gf28.js
git commit -m "gf28: log/exp 查表"
# 推到遠端，開 PR 合併
git push -u origin feat/gf28

AI 協作的關鍵不是「叫它寫」，而是「先講好介面」
有了規格與測試，AI 產出的程式碼可以被驗證； 沒有規格，三個人（和三個 AI）寫出來的東西誰也接不起來。
